# rewire — Design Decisions

Status: agreed via design interview, 2026-11-20. Working name: `rewire` (check npm / crates.io / GitHub / trademark before public release).

## Vision
The go-to **anti-slop software factory**: a factory-first coding harness whose primary product is the verification and review layer, not code generation. It must never ship slop, and the codebase must not degrade over time as it writes more code.

## Definition of slop
1. Broken — doesn't compile, fails types, breaks existing tests
2. Fake verification — tautological/over-mocked/weakened tests, unevidenced "done", skipped checks
3. Spec drift — wrong problem, partial implementation, silent scope cuts
4. Security — injection, secrets, unsafe defaults, vulnerable/hallucinated deps, missing authz
5. Silent failures — swallowed errors, catch-all fallbacks, TODO/placeholder logic in shipped paths
6. Bloat — over-engineering, needless abstraction, duplication instead of reuse, dead code, comment noise
7. Convention drift — ignores repo patterns, naming, architecture, existing utilities
8. Maintainability — high complexity, unclear naming, poor structure
9. Entropy — cumulative degradation across many individually-acceptable changes

## Decisions from live runs
Source: the first live real-model run, 2026-11-24.

| # | Area | Decision |
|---|---|---|
| 28 | Criterion kinds | Every acceptance criterion has a `kind`: `change` (new or corrected behaviour) or `preserve` (behaviour that works today and the task says must keep working). The red check requires a `change` test to fail now with an assertion error and a `preserve` test to pass now; after implementation every frozen test of either kind must pass. A contract needs at least one `change` criterion (the spec stage retries once, then fails with `contract_without_change`; a contract with open questions goes to clarification first), and every test must make an assertion, which the red check proves with a harness-owned no-assertion probe in the same run (`assertion_rule_unenforced` if the runner does not fail it). A preserve test that fails now is terminal, never retried (`preserve_fails_now`): the run escalates and asks the human whether the criterion is mislabelled or the test is wrong, because a retry could only turn it green by weakening it. The one exception is a test-writer mistake: a preserve test whose every failure is a non-assertion error thrown in the test file itself (its first stack frame outside `node_modules`, e.g. calling a function that does not exist) gets the ordinary single retry, told to keep its assertion. An assertion failure, an error thrown from the code under test (a crash bug labelled `preserve`), or a failure with no parseable stack stays terminal. Residual risk: a bug that makes the code return a wrong value the test then dereferences (a TypeError in the test file) is retried; the retry is told not to weaken the test and the spec-compliance reviewer still checks the labels against the task. **Why:** on the live run the task was a bug fix that said "everything that works today keeps working"; the spec stage correctly wrote preserve criteria (existing function unchanged, invalid width still throws, whitespace still collapses), but the red check required every new test to fail, and a test for working behaviour passes by definition, so the run escalated with `red_check_failed`. Any bug fix with "keep working" criteria could never pass the stage. The faux-model CI never wrote such a contract. **What is and is not caught:** a bug labelled `preserve` whose test exercises the bug fails now and stops the run (`preserve_fails_now`). A bug labelled `preserve` whose test does not exercise it (written weak from the start) passes the red check, and nothing in the harness hard-blocks it; the spec-compliance reviewer and the verifier get the task text (fenced as untrusted) and are asked to report a preserve criterion that is really the requested change, and the report shows every criterion's kind next to the task for a human. `kind` is required with no default: contracts are parsed only from the spec model's output (contract.json is never read back), and a silent default would hide an unlabelled criterion. Refactor-only tasks (no `change` criterion) are out of scope for v0.1 |

## Decisions for interactive mode
Source: the interactive TUI design (branch `feat/tui`), 2026-11-25.

| # | Area | Decision |
|---|---|---|
| 29 | Interactive session | `rewire` on a TTY opens a chat, then hands code changes to a gated run. The chat agent cannot write: its tools are `read`, `grep`, `find` and `bash` under the sandbox `chat` profile (no repo writes, scratch dir only, network denied). It has no `write` or `edit` tool. The chat model is the author model (`routing.spec`). One gated run is active at a time. Sessions are stored redacted in `.rewire/sessions/<id>.jsonl` and can be resumed. **Why:** every code change must pass the same hard gates and independent review as `rewire run`, so the conversational surface gets no write path of its own. **Accepted trade-offs:** chat `bash` ignores abort and runs to its own timeout (up to 600 s); it cannot write the repo, so the cost is a stray sandboxed process. Ctrl-C at a proposal card or the in-app trust prompt exits 0 (the chat is persisted and resumable) instead of dismissing the card. A `.rewire/sessions` file committed to a cloned repo is treated as the user's own history: `/resume` lists it (reading at most 64 KiB for its title) and replays it to the chat model like any stored session; the chat stays read-only and a proposal still needs `y`. |
| 30 | Claude skills | User skills load automatically from `~/.claude/skills` and `$XDG_CONFIG_HOME/rewire/skills`. Repo skills (`<repo>/.claude/skills`) load only after trust is pinned to a sha256 over all their files. The hash includes shadowed repo skills (a user skill with the same name wins), so the trust prompt lists them. A changed hash asks again. The trust store is `$XDG_CONFIG_HOME/rewire/trusted-skills.json`, updated with a locked read-merge-write. Skills are read on the host and snapshotted once per session; a trust granted mid-session takes effect on `/clear`. Skills reach the chat, spec, test-writer and implementer only, never the reviewers or the verifier. **Why:** a skill is instruction text from outside the contract. Repo skills are attacker-controllable, so they need an explicit, content-pinned approval, and the stages that judge the result must not be steered by them. The sandbox denies `~/.claude*`, so skills are read on the host and materialised under `$XDG_CACHE_HOME/rewire/skill-sets` (deliberately not the OS tmp dir, which the Linux sandbox replaces with a private tmpfs). On Linux, an `$XDG_CACHE_HOME` under `/tmp` therefore leaves a skill's bundled files unreadable inside the sandbox (SKILL.md itself still loads); the default `~/.cache` is unaffected. **Ruling:** the planned `skill_untrusted` error code was not implemented; pending repo skills are simply not loaded and `/skills` lists them as pending. A skill dir rejected at discovery (e.g. a symlink) is shown as a warning line at TUI start, and an unreadable trust store leaves repo skills unloaded with a warning instead of blocking the session. **Accepted residual:** skill text can still reach the reviewers indirectly, through the contract or the diff that an author stage produced. |
| 31 | Checkpoints | A run can pause for approval at `contract`, `tests` and `commit`. In the TUI, `contract` and `tests` are on by default and `commit` is off (`/checkpoints` changes it per session). Without a `checkpoint` input (`rewire run`, headless) nothing pauses. The contract checkpoint accepts `approve`, `revise(note)` or `stop`; the tests and commit checkpoints accept `approve` or `stop`. Revise is limited to 3 per run, and a 4th is recorded as `stop`. `stop` escalates with reason `stopped_by_user` (exit 2). An invalid decision escalates with `stage_error` and fixed preset text. Ctrl-C at a pending checkpoint ends the run as `interrupted`. Every decision is in `events.jsonl` and `report.md`. **Why:** approval must be possible without making the gates optional. A bounded revise loop keeps a run from becoming an open-ended chat, and a protocol fault must stop the run without asking a model to explain it. |
| 32 | Terminal text and approval | **One terminal sanitizer.** `sanitizeTerminal` in `@rewire/core` is the only one. It is a single linear scan that drops CSI and ESC sequences, OSC/DCS/SOS/PM/APC strings (7-bit and 8-bit), C0/C1 controls except newline and tab, CR, the Unicode default-ignorable code points (tags, variation selectors, zero-width and bidi marks, fillers) and U+2028/2029. The TUI's `sanitize` is that function. `stripControls` is the same function with tabs dropped as well. This changes #23 output in the report, the commit title and the headless stream: a terminated control string is removed whole, including its body and a CSI's final byte (the old regexes left parts of it). A string with no terminator before a newline or the end loses only its introducer, so mojibake such as `â€\u009d` cannot swallow the rest of a report. **Approve exactly what is shown.** `propose_run` refuses a task that the sanitizer would change, telling the model to resend plain text, and stores the accepted task redacted. The proposal card (`<Safe>` = `redact(sanitize(x))`) therefore shows exactly the string the run starts with. **Transcript.** Finished transcript entries are printed once through Ink's `<Static>`, cut to the terminal width at the time they are printed. They do not re-flow on resize. `/clear` and `/resume` start a new static region under a separator line. **Why:** hidden text in an approved task would reach the spec model as trusted input, which is the same "approve what was shown" property that the skill trust pin guarantees. Two sanitizers would drift. A transcript in the dynamic frame was rewritten, and duplicated into scrollback, on every keystroke once it was taller than the screen. |
| 33 | TUI parity with Claude Code / Codex | The interactive session streams replies, renders Markdown with syntax-highlighted code, shows tool calls as `● Name(args)` with a `⎿` preview, a spinner, a header box and a status line, a `/` command menu, an `@` file picker and checkpoint cards with scrollable views. **Streaming only from the chat.** Streaming is opt-in through `onDelta` on a provider call; only the chat agent passes it. Without it every provider sends the same non-streamed request as before. A pipeline test pins this: it wraps the providers of a faux pipeline run (reviewers and verifier included) and asserts that no call carries `onDelta`, while a faux-provider snapshot pins the stages' prompts and tool lists. So the pipeline, `rewire run`, `--headless`, the exit codes and the reports are unchanged. A stream that fails mid-way maps to the same codes as a non-streamed call (`ollama_timeout`, `ollama_request_dropped`, provider errors, `aborted`), and the Ollama reply timeout bounds the call (for a stream, how is #37). A throw from the `onDelta` callback itself fails the call with the new code `provider_stream_callback_failed`, never as a transport error. **Sanitize, then redact, the whole buffer.** Streamed text is rendered as `redact(sanitizeTerminal(buffer))` over the whole accumulated text on every render (throttled to 50 ms), never per delta, and only then split or capped, so an escape sequence or a key split across deltas, or a key split by an SGR sequence, is still caught. The same order applies to tool previews, the commit diff view and the contract and test views. **Scrollback.** Finished parts of a reply leave the live area as they finish: a tool line once its result arrives, text once its model call ends, and each complete top-level Markdown block as soon as the next one starts. A block is split off only at a blank line where cleaning the parts gives exactly what cleaning the whole buffer gives, so a split cannot cut a key or an escape sequence. They print once through `<Static>`, and only the block still streaming stays live, cut to the terminal height (its tail shows). A live area taller than the terminal would be re-printed into scrollback on every frame (DD #32). Chat events that arrive after their turn ended are dropped. Markdown is lexed from already clean text, and every leaf string is cleaned again after lexing, because `marked` decodes numeric references (`&#x1b;`) back into control characters. Markdown and highlighting become Ink `<Text>` segments with colour props, never raw ANSI. **Caps.** Lists and quotes nest at most 8 deep (deeper renders as plain text: unbounded nesting crashes yoga-wasm); a code block with a line over 2,000 characters, more than 5,000 lines or over 50 KB renders unhighlighted (highlight.js is quadratic on long tokens); highlighting is memoized per finished block; only the registered grammars are bundled. **Esc versus Ctrl-C.** Esc interrupts the chat reply in flight: the abort signal stops the provider request, the text already streamed stays on screen marked `Interrupted by user`, and the turn is not stored. Esc never aborts a gated run; Ctrl-C keeps its meaning (it aborts a run or a turn, quits when idle, and a second press within 1 second exits 130). Esc still cancels the revise box and closes the `/` menu, the `@` picker and a checkpoint view. **`ctx`** in the status line is the last chat model call's input plus output tokens, the size of the chat's context, as Claude Code and Codex show it, not a sum over the session. **The `@` picker only inserts a path.** It lists `git ls-files` on the host, spawn-streamed and killed once 5,000 usable paths are in (paths with control or terminal-unsafe characters are dropped). Choosing one inserts the path text; the chat agent reads the file with its own sandboxed tools, so the picker grants no access the chat did not already have. **Why:** the session should feel like the agents people already use, without letting the polish reach the gated pipeline or the terminal. Streaming in the pipeline would add a failure mode to every stage for a view nobody watches; per-delta cleaning misses anything split across chunks. Esc is the common interrupt key in both reference tools, but a run is expensive and has its own report, so it keeps the deliberate Ctrl-C. **Accepted residuals:** a key split by a literal newline is not redacted (inherent to the redact patterns; a fragment of a wrapped key can show in a preview); OpenAI and Anthropic streams have no wall-clock bound of their own (only the TUI streams, and Esc aborts a hung stream); `ctx` counts chat calls only, not a run's stages. |
| 34 | Chat context compaction | **A checked record, not a summary.** The chat's context is compacted into a structured session record (`goal`, `constraint`, `preserve`, `decision`, `open_question`, `preference`, `next_step`, `note`). Each item has a `source` (`user` or `inferred`), evidence (`{messageId, quote}`) and a status. A separate `observed` block (files read, commands and their exits, tool failures) is computed by code from stored messages, never by the model. Its schema also has a `runs` list, which the chat session never fills in v0.1 (the chat model does not see run outcomes; see the residuals). The model returns operations (`add`, `update`, `resolve`, `supersede`) and code applies them. **Authority rules, all checked by code.** (1) Every cited quote must appear verbatim in the cited stored message (after the store's sanitize and redact); quotes under 12 characters must be the whole message. (2) A `user` item can be created, changed or superseded only with evidence from user-role messages. Tool output, file contents, skill text, assistant text and the existing record never create or override one. (3) The evidence for changing a `user` item must be in the compaction window, or recent, or pending (see below). (4) It must also be newer than the item's newest evidence (`stale_evidence`), so an old instruction cannot overturn a newer one. (5) Superseding a `user` item needs `by.source` user. (6) One op per item per compaction (`duplicate_target`), and a snapshot check (`state_changed`) rejects an op whose target changed since the verifier saw it. (7) A `skill` or `recall` tool result is never evidence: an op citing one is rejected (cite the original message). (8) An `inferred` item that no user message supports (its evidence cites only tool results or assistant replies, or nothing) gets a code-set `notFromUser` flag and renders as `[inferred, not from the user …]`. The chat prompt and the record preface say that only `[user …]` items carry the user's authority and that `inferred` items are the compactor's reading, never instructions. So a file line such as "the user has decided X" can at most become an item visibly marked as not from the user, and a goal, constraint, preserve or decision that cites only it is applied only if the verifier accepts it (below). **No silent loss.** An item leaves the active record only through `resolve` or `supersede` with evidence, and goes to the archive (capped at the newest 500 in the stored line; the full history stays in the message log). A user message cited by an op that was rejected for a reason other than a failed authority check (a verifier reject, `duplicate_target`, `verification_budget`) stays citable for 3 compactions (`pending`), so a junk op cannot block a later correction. A compaction that fails (invalid output after one retry, a provider error, a violated invariant, an unavailable verifier) keeps the previous record and the raw messages since it, shows one dim line, and the session continues. When a window was split into parts, the parts already applied stay and the context ends there. After a failure the automatic trigger is held back until the context has grown by a quarter of the limit, capped at a ceiling of `limit + 0.5·(0.85·W − limit)`; an attempt already at or past that ceiling turns automatic compaction off for that window (`stuck`, shown once; `/compact` still works, and a changed window clears it). The `recall` tool searches all stored messages and the archive, so detail that left the context can be found. **Cross-family verifier.** Risky ops (`isRiskyOp`: any op on a `user` item; an add or supersede that creates a `user` item; any update, resolve or supersede of an open question; and an add, update or supersede that leaves an inferred goal, constraint, preserve or decision resting on tool results with no user message among its evidence) go in one batch to the run's verifier model (`routing.verifier`), from a different family than the chat model when the routing allows it. It sees the op, the target item as it is in the record, the cited messages and whether they are in the window, all fenced and cleaned (never skill text or `recall` output, which cannot be cited), and answers with exactly one JSON object (anything else is retried once, then rejects). An explicit reject drops that op. If the verifier is unavailable, times out (180 s) or never decides, the whole compaction fails, because skipping the check would let an unchecked change through. **Deterministic rendering.** The record the model sees is rendered by code from the record, under a budget, inside `fenceUntrusted` (`untrusted_session_record`). Nothing rendered is stored: a compaction line stores the record, the compaction point (`since`), the retained range and any cut of its newest message (`retainedFrom`, `truncated`), the fence id and the render budget. A `recordMessage` or cut `content` found in an older or forged line is ignored. On resume the context is rebuilt from those fields and the stored messages, so it is byte-identical and the prompt prefix stays stable for caching; a cut is measured and applied on the redacted text the store writes, so it lands on the same characters live and after a resume. **Context shape.** After a compaction the context is the system prompt, the record, one message of the most recent user messages verbatim (budget min(`recent_user_tokens`, 0.25·limit); the newest alone over it is cut head and tail), and the turns after that point. Assistant and tool turns from the compacted region are dropped. Compaction splits a window too big for the model's prompt into consecutive parts, each stored on its own. Only the last part's context is fitted: to a target of min(0.5·limit, limit − the pending message), first by halving the retained budget (down to none), then by halving the record's render budget (down to 0; `user` items are never dropped). If even that smallest form is over the target, the compaction still applies, reports `overBudget`, and holds the automatic trigger back the same way as a failure (or marks it `stuck`). So the result is not guaranteed to be under half the limit: many long `user` items on a small window can keep it above. **Trigger.** The limit is the smallest of: the formula `min(0.85·W, 32768·(W/32768)^0.6)` rounded down to 1000, or instead the calibrated value when one exists (which may be above the formula); 0.85·W rounded down to 1000; and a latency candidate (measured prompt-reading rate × `latency_budget_s`, after 2 samples; a sample counts only the tokens the server read after the prefix it shares with the previous request, #39). The first sample after a model load is skipped (it includes load time). That value is raised to at least 4096 and then capped at 0.85·W, so a window under about 4.8K gets a limit below 4096. A configured `[compaction.models."<ref>"] limit` replaces the computation and is floored at 4096 but not capped. `rewire calibrate` measures the effective context with planted-fact probes, never runs by itself, and requires `--yes` on a paid provider; its results are keyed by model digest and window and go stale when the window moves more than 10%. The plan asked for "a token and cost estimate" before a paid run; the code prints an input-token count only (rewire has no price table) and exits with `calibration_failed` without `--yes`. Compaction applies to the chat only. `rewire run`, `--headless` and every pipeline stage are unchanged, and skills, `recall` and the record never reach the pipeline's reviewers or its run verifier (#30). The compaction verifier is a separate checker: it sees the record item it judges, but never skill text or `recall` output. **Why:** a summary written by the model is unchecked prose, and the first thing it forgets is a constraint, or it keeps a line a file injected. A record whose edits code verifies, whose user-authority is tied to user messages, and whose removals leave a trace gives long chats a memory that cannot be rewritten by tool output and that fails closed. A second family checks the edits that matter because a model reviewing its own edit shares its blind spots. The formula comes from the observation that long contexts are read less reliably and re-read every turn, so the limit grows slower than the window; calibration replaces that guess with a measurement when it matters. **Accepted residuals:** judgement in `inferred` items can be wrong (code checks the quote exists, not that the inference is sound); the formula constants (0.85, 32768, 0.6) are judgement; a key split by a literal newline is not redacted (as in #33); with a single model the verifier is not independent, and the TUI shows a notice; a provisional window (Ollama before its first reply, faux) is not checked for staleness against a calibration until the first turn refreshes it; a hung, abandoned compaction blocks the next `/compact` (compactions queue); calibration is slow on local models, and two calibrate runs at once are not locked against each other (each write is atomic, the last writer wins); an inferred item resting on an assistant reply that repeats injected text is marked not-from-the-user but is not sent to the verifier (only evidence that cites a tool result and no user message is), because routing every assistant-backed decision through it would cost a verifier call on most compactions; `observed.runs` is never filled by the chat (feeding run outcomes would need the session to learn and persist them, a new channel into the record, for a fact the TUI already shows); the same session resumed in two processes at once interleaves message ids, so compaction lines from one are refused by the store and its automatic compaction ends `stuck` (a conflict check on append would need a new error code and a reopen path, and concurrent writers were already unsupported before compaction); on a very small window (W under about 6K) the compactor's prompt budget is about 1,000 tokens, close to its own system prompt, so a compaction becomes one model call (and possibly a verifier call) per turn of the window: slow on a 4K Ollama model, but never unsafe. |
| 35 | Cloud and API providers | **Platform clients, not a changed URL.** Claude on Bedrock, Vertex and Foundry uses each platform's own SDK client (`AnthropicBedrockMantle`, `AnthropicVertex`, `AnthropicFoundry`), so signing (SigV4, Google ADC, Foundry key header) and URL shapes are the SDK's, and the request body is still `toAnthropicParams`. Azure OpenAI uses `AzureOpenAI`; Gemini and `[endpoints.<name>]` use the OpenAI client against an explicit `baseURL`. Router or meta ids (`auto`, `router`, `default`, `openrouter/...`) fail closed with `model_ref_invalid` unless `family` is set; bedrock, vertex and foundry accept Claude only. Doctor prints resolved values and env var names only, hides values of an unusual shape as `(set, unusual format)`, and treats an unused broken table as a note. The calibrate paid gate covers every provider except ollama, faux and loopback endpoints. Cloud SDKs are imported lazily (they are not loaded unless used) but are bundled in the npm package. `rewire run` and `rewire chat` create every routed role's provider once before starting (creation only resolves settings and env, with no request), so a misconfigured reviewer or verifier fails with `provider_auth_missing` before anything is billed, not at its stage; the pipeline still creates its own. Azure `api_version` is required (the SDK has no default) and the endpoint must be the resource root. No new error codes. **Accepted residuals:** an unrecognised leading word in a model id counts as its own family, so an exotic id can pass as independent (set `family`); the Vertex fix for unhandled credential rejections reads the SDK's private `_authClientPromise` (a test guards it); loading ADC cannot be aborted; Azure `max_completion_tokens` may be rejected by very old API versions; Gemini's output-cap field `max_tokens` is documented on Vertex's compatibility page but not confirmed against Gemini's own reference; bundle growth (sheperd tarball 1,137,726 to 1,608,352 bytes, +41%; `dist/main.js` about +2.4 MB unminified); a secret shaped like a resource name could still be printed by doctor (a malformed region or resource is never echoed in an error); doctor exits 1 for a used but incomplete provider; the calibration cache is keyed by `<endpoint>:<model>` and the window digest, not the endpoint's `base_url`, so re-pointing an endpoint at another server keeps the old result until `rewire calibrate --fresh` (mixing the URL in would invalidate every existing cache entry); the cloud and OpenAI-compatible clients still honour `ANTHROPIC_LOG`/`OPENAI_LOG` from process.env, as the first-party providers do (debug output only, never a request change). **Not supported:** Claude subscription login, because Anthropic does not permit third-party apps to offer Claude.ai login or route requests through Free, Pro, Max or Ultra credentials. |
| 36 | Session routing overrides (`/model`) | **Session only.** A `/model` pick overrides one role for this TUI session: effective overrides are the models file's `[roles]` overridden by the picks, and the routing is `resolveRouting(available, effective)`. Nothing writes `models.toml`, so a pick made to try a model cannot silently become the routing of every later run, and `default` drops the pick. **The refusal rule.** A pick that puts the reviewer or the verifier in the implementer's family (`modelFamily`) is refused while `available` holds another family, with a message naming both families; independence is the point of the review, and a picker must not make it worse in one keystroke. A pairing already in effect, or the models file's own, is exempt: a file may deliberately pin a same-family reviewer, and without the exception every unrelated pick would be blocked and `default` could not get back to the file. With one family only, the pick applies and its note says `same-family`, as the report would. Every provider must be creatable (`createRoutedProviders`, no network) or the pick is refused; a refusal changes nothing. **Plan, then commit after the rebuild.** `RoutingControl.plan` validates a pick without applying it. When the pick changes `spec` (the chat model) or the verifier (which checks the chat's compaction), the CLI first rebuilds the chat session on the candidate routing by resuming the same session id through the `/resume` path, so the messages, session record and compaction state carry over and the new model's context window is looked up as at session start; only then is the pick committed, and the TUI installs the new session before the old one can send again. A failed build leaves routing, providers and session as they were. A session with no completed turn has no id and starts fresh. The rebuild re-discovers and re-resolves the skills like `/resume`, so a skill trusted earlier in the session takes effect at that pick. The family rule covers the pipeline pairing only: a chat or verifier pick may make the chat's compaction check same-family (verifier and chat model share a family); that is not refused, and the rebuilt session's notices (the compaction same-family notice) are shown as at start, `/clear` and `/resume`. **Never mid-run.** Picks are refused while a run is active, a chat turn, compaction or session change is in flight, and a run started during a pick's build fails with `run_in_progress`; a run reads `current()`, a frozen snapshot, at start and keeps it. **Accepted residuals:** the welcome header already in the scrollback is `<Static>` and is not redrawn (the next `/clear` or `/resume` header shows the new routing); without compaction the token count is blank after a pick until the next turn, since it comes from the last usage event; the TUI's busy check in `applyPick` (a turn or compaction in flight) is defensive and untested, because the input is off in those states. `/skills` is the same kind of list: browse with details (a symlinked skill dir is followed once, as discovery follows it, and shown as `linked → <real path>`; links inside it are listed and never followed), its review row opens the existing trust prompt, a run's checkpoint or clarification closes it, and there are no enable/disable toggles because no such feature exists. |
| 37 | Ollama reply timeout: first chunk, then idle | **Streams fail on silence, not on length.** A streamed Ollama reply (`onDelta`, only the TUI chat) gets the reply timeout only until its first chunk, which is the prompt-reading time. After that it fails only when no chunk of any kind (text, thinking, tool-call delta) arrives for `OLLAMA_IDLE_TIMEOUT_MS` (120 s). The timer resets on every chunk, and there is no total cap while chunks flow. The caller's signal (Esc) still aborts. Idle expiry is `ollama_timeout` with "no output for 120s", distinct from the first-chunk message. Non-streamed requests (every pipeline stage) keep one total timeout. The SDK's per-request `timeout` stays just past ours: the SDK clears it once headers arrive, so on a stream it bounds only the wait for headers and cannot cap a started stream. undici's headers and body timeouts stay off. **Two sources, with provenance.** The reply timeout is `REWIRE_OLLAMA_TIMEOUT_S`, else `[providers.ollama] timeout_s` in models.toml (an integer from 1 to 86400), else 900 s, raised from 300. `resolveOllamaTimeout` returns the value and its source. `ollama_timeout` names both, and on the default its hint says the variable is not set in this process. `rewire doctor` prints `reply timeout 900s (default|env|models.toml)`. The run hands the resolved value to the preflight smoke test (`RunPipelineInput.ollamaTimeout`). **Why:** a live run failed with `timed out after 300s`. The variable was in `~/.zshrc`, but the terminal that launched rewire was opened before the edit, so the process ran on the default. Separately, a 27B local model reading a 14K to 36K token chat context and then thinking can pass any fixed total limit while it is still streaming. A total limit on a live stream cuts off a working model; an idle limit catches only a stalled one. A setting in the models file does not depend on which shell started the process, and naming the source makes the stale-terminal case obvious. **Accepted residuals:** a model that streams forever without finishing is bounded only by Esc (or `max_tokens`). A `runPipeline` caller that does not pass `ollamaTimeout` (bench, for one) runs the preflight smoke test on `REWIRE_OLLAMA_TIMEOUT_S` or the default, ignoring `[providers.ollama] timeout_s`; the stages still use the provider's own resolved value, and the smoke test is a tiny request. `rewire calibrate` gives Ollama probes no second timer of its own, so a timeout surfaces as `ollama_timeout` with its source. |

| 38 | Web access | **Two host-side tools for three stages, with web text fenced as data.** `web_search` (Ollama by default, or Tavily, Brave or SearXNG) and `web_fetch` (`@rewire/web`, wrapped in `@rewire/tools` `createWebTools`) run in the rewire process, not in the sandbox. Only the chat, the spec stage and the implementer get them; the test writer, the reviewers, the verifier, compaction and its verifier never do, which tests assert as for skills in #30. They are on by default where the CLI passes `WebAccess` (not in faux mode), and `.rewire/policy.toml` `[web]` turns them off or narrows them, tighten-only: `enabled` can only go false, `deny_domains` is a union, `allow_domains` intersects. An empty allow list removes the tools (`webOffReason`). The policy covers the search service too: a query goes to the backend's host (`searchServiceHost`: ollama.com, api.tavily.com, api.search.brave.com or the SearXNG host), so `web_search` is refused when that host is outside a set `allow_domains` or matches `deny_domains`. `rewire run --no-web` adds `enabled = false` as the run layer, which the benchmark passes on every run, so no fixture policy can turn web on. Every fetch target is resolved and refused if any address is private, loopback, link-local, CGNAT, multicast or reserved (IPv4 inside IPv6 judged as IPv4, Teredo refused). The connection is pinned to the checked address, and each redirect is checked again, up to 5. A query or URL with a secret-shaped value is refused before sending, by `checkOutgoing`, which decodes percent-escapes to a fixpoint, folds NFKC, drops controls and has unguarded `sk-`/`ghp_`/`AKIA` patterns (`SECRET` also matches `tvly-` keys). Brave and Ollama keys have no fixed shape, so the tools also refuse a query or URL that holds the literal value of a search key set in this process (raw or percent-encoded, any case, 8 characters or more) and redact those values from web text. Every incoming title, URL, snippet and page is NFKC-folded, has controls removed, is redacted and returned inside an `untrusted_web` fence. The agents' prompts say web content is data; those sentences are added only when the tools are, so a run or chat with web off is byte-identical to one without web. Every call emits a `web_request` audit event. The web tools give the loop a `summary` hook, so `tool_call` events log `"<query>"` or `<host><path>`, or `[refused: secret-shaped]`, never the raw arguments. A `storedArguments` hook makes the loop keep `{refused: "secret-shaped"}` in the history in place of a refused call's arguments, so the model's own key-bearing arguments never reach the session file, the spec digest or a later prompt; the tool still runs with the real ones. The tools also return display-only `ToolResult.preview` lines (title · host, or a status line with the size the model got, then the page's first line), which the TUI shows and the model never sees. **Why host-side:** the sandbox's network allowlist stays empty (#26), so no agent `bash` can reach the network. One process-side client can apply the SSRF guard, address pinning, the outgoing check and policy at one choke point, which a sandbox network exception cannot (Seatbelt and bwrap cannot filter by domain). **Why these stages:** the author stages benefit from documentation and API lookups. The test writer must test the contract, not a page, and the checking roles must judge only the repo, the contract and the diff, so a page cannot steer a verdict. **Why the fence:** a page is untrusted input like repo text (#23), and a fence it cannot close keeps it out of rewire's instructions. **Why the summary hook:** the loop logged tool arguments raw, and `redact`'s token-start guard lets `x<key>` through, so a refused secret would have reached `events.jsonl`. **Accepted residuals:** a page can still mislead the model's reasoning; the gates and review check the result, not the sources. With web on, repository text that is not secret-shaped can leave in a query or URL (prompt injection, or the model's own choice). `enabled = false` stops it. `allow_domains` limits it to the listed hosts, which can still receive text in URLs, and in queries when the search service's host is listed. A Brave or Ollama key (or any unprefixed secret) that is not the value configured in this process is not recognised. Re-encoded keys (base64, reversed, split across host labels, overlong UTF-8) are not caught. Other tools' `tool_call` summaries (a `bash` command, for one) still use display redaction only. Known false positives that fail closed: an `sk-` word followed by a 20+ letter word (`ask-about-internationalization`) and `akia…` host labels. NFKC changes how web text reads to the model (full-width forms become ASCII). A cancelled chat turn's calls are still reported, because their requests went out. Chat `web_request` events are shown live and not written to disk; a run's go to `events.jsonl`. The SearXNG URL is user-configured and not SSRF-checked. |

| # | Area | Decision |

| 39 | In-turn context budget and prefill guard | **RCA.** One user message led to 14 tool calls in one turn, three of them `read`s of about 64 KB, so the chat context grew from 7K to 107K tokens inside that turn, where compaction (#34, user boundaries only) never applies, and at about 90 tokens/s the 107K prompt could not be read within the 900 s reply timeout (`ollama_timeout: no output within 900s`). The latency limit that should have caught it stayed on the formula (`75k (f)`) because the meter divided the whole prompt by the time to the first chunk: on a prefix-cache hit (4,415 tokens with 126 uncached) that measures the cache at thousands of tokens/s, which puts the latency candidate above the formula, and the honest 13-minute reads that followed were then more than 5 times slower than that inflated rate and were discarded as model reloads, so the meter never corrected. **In-turn clearing.** Before each model call of a chat turn (compaction on), while the estimate (`TokenEstimator`, the request's system prompt, tools and messages) is over the compaction limit, the oldest tool results of the current turn are replaced, in the request only, by a fixed stub: `[tool output cleared to fit the context: <label> — <N> chars. Run it again (with offset/limit for read) if you still need it, or use recall after this turn.]`. The 2 most recent results are never cleared, and a result no longer than its stub is left alone. `<label>` is the tool's `summary` hook (web), else chosen fields of the chat tools (`read` path, offset and limit; `grep` pattern and path; `find` glob; `bash` command; `recall` query; `skill` name), else the tool name, sanitized, redacted and capped at 120 code points; never the argument object. A cleared result stays cleared for the rest of the turn (a map by call id), so after each clearing step the prompt prefix is stable again. Only the content changes, so every `tool_call`/`tool_result` id pair stays as it was for every provider. The stored messages, `history()` and the next turn's context keep every result whole; compaction at the next user boundary handles them, and `recall` finds them once the turn is stored. Each step that clears emits `context_cleared` (`cleared`, the token target, `reason`), shown as one dim line, `⎿ cleared 3 earlier tool outputs to fit the context (75k limit)`. **Prefill guard.** With `replyTimeoutMs` (the CLI passes the resolved Ollama reply timeout for an Ollama chat model only) and a measured reading speed (1 sample is enough here), a call whose estimated prompt divided by that speed exceeds 0.8 × the reply timeout clears more, down to the newest result alone; if it is still over, the request is not sent and the turn fails with `ollama_timeout` (the code a sent request would have ended with, so no new code), saying the context is too large for this model's reading speed and pointing to `/compact`. A failed turn stores nothing, as before. The guard uses the whole estimated prompt, not the uncached part, because Ollama did not keep the cache at these sizes. **Meter fix.** A sample now counts only the tokens the server had to read: the reported input tokens minus the previous call's, when the request starts with the whole previous one (same system prompt, tools and messages), or minus an estimate of the shared messages (never more than the previous count). Under 1,000 tokens read is not a sample, which drops cache hits; the reload check compares against the same read count. **Stable system prompt.** The chat's system prompt is built once per session. The skills index is fenced with a fresh random id on each render, so rebuilding it per turn changed the prompt's first bytes at every user message and no prefix cache spanned two turns (the server log shows `matched=2` and `matched=0` at each new message). **Per-model meter.** The TUI keeps one meter per chat model, so a `/model` pick no longer inherits another model's speed. **Why:** a turn is the unit that runs unattended; a limit that applies only between messages cannot bound it. Clearing the oldest results first keeps what the model is working on now, a fixed stub keeps the prefix cacheable, and refusing a request that cannot be read in time fails in a second instead of after 15 minutes. **Accepted residuals:** a cleared result is gone from the model's view for that turn; the model may read it again, which costs a call. The limit and the guard rest on the estimator, so a prompt far denser than its estimate can still pass. When the newest one or two results alone are over the limit, the turn still goes over it (only the guard, on Ollama with a measured speed, refuses). The guard can refuse a prompt a warm cache would have read in seconds. The prefix arithmetic assumes the server kept the previous prompt's cache; when it did not (a model swap), a sample undercounts what was read, which errs toward a lower limit, and a far-off one is discarded by the reload check. Results of earlier turns are never cleared in-turn: when compaction is held back or stuck, a turn can start over the limit (the guard still applies). **Pipeline (out of scope):** the implementer has the same exposure. Its loop also accumulates tool results for up to `maxTurns` calls with no in-turn budget, and its requests are not streamed, so on Ollama the total reply timeout covers reading and generation; a long implementer turn on a slow local model can end in `ollama_timeout` the same way. Pipeline behaviour is unchanged here. |
