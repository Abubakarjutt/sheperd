# rewire — Design Decisions

Status: agreed via design interview, 2026-11-20. Working name: `rewire` (check npm / crates.io / GitHub / trademark before public release).

## Vision
The go-to **anti-slop software factory**: a factory-first coding harness whose primary product is the verification and review layer, not code generation. It must never ship slop, and the codebase must not degrade over time as it writes more code.

## Definition of slop
1. Broken — doesn't compile, fails types, breaks existing tests
2. Fake verification — tautological/over-mocked/weakened tests, unevidenced "done", skipped checks
3. Spec drift — wrong problem, partial implementation, silent scope cuts
4. Security — injection, secrets, unsafe defaults, vulnerable/hallucinated deps, missing authz
5. Silent failures — swallowed errors, catch-all fallbacks, TODO/placeholder logic in shipped paths
6. Bloat — over-engineering, needless abstraction, duplication instead of reuse, dead code, comment noise
7. Convention drift — ignores repo patterns, naming, architecture, existing utilities
8. Maintainability — high complexity, unclear naming, poor structure
9. Entropy — cumulative degradation across many individually-acceptable changes

## Decisions from live runs
Source: the first live real-model run, 2026-11-24.

| # | Area | Decision |
|---|---|---|
| 28 | Criterion kinds | Every acceptance criterion has a `kind`: `change` (new or corrected behaviour) or `preserve` (behaviour that works today and the task says must keep working). The red check requires a `change` test to fail now with an assertion error and a `preserve` test to pass now; after implementation every frozen test of either kind must pass. A contract needs at least one `change` criterion (the spec stage retries once, then fails with `contract_without_change`; a contract with open questions goes to clarification first), and every test must make an assertion, which the red check proves with a harness-owned no-assertion probe in the same run (`assertion_rule_unenforced` if the runner does not fail it). A preserve test that fails now is terminal, never retried (`preserve_fails_now`): the run escalates and asks the human whether the criterion is mislabelled or the test is wrong, because a retry could only turn it green by weakening it. The one exception is a test-writer mistake: a preserve test whose every failure is a non-assertion error thrown in the test file itself (its first stack frame outside `node_modules`, e.g. calling a function that does not exist) gets the ordinary single retry, told to keep its assertion. An assertion failure, an error thrown from the code under test (a crash bug labelled `preserve`), or a failure with no parseable stack stays terminal. Residual risk: a bug that makes the code return a wrong value the test then dereferences (a TypeError in the test file) is retried; the retry is told not to weaken the test and the spec-compliance reviewer still checks the labels against the task. **Why:** on the live run the task was a bug fix that said "everything that works today keeps working"; the spec stage correctly wrote preserve criteria (existing function unchanged, invalid width still throws, whitespace still collapses), but the red check required every new test to fail, and a test for working behaviour passes by definition, so the run escalated with `red_check_failed`. Any bug fix with "keep working" criteria could never pass the stage. The faux-model CI never wrote such a contract. **What is and is not caught:** a bug labelled `preserve` whose test exercises the bug fails now and stops the run (`preserve_fails_now`). A bug labelled `preserve` whose test does not exercise it (written weak from the start) passes the red check, and nothing in the harness hard-blocks it; the spec-compliance reviewer and the verifier get the task text (fenced as untrusted) and are asked to report a preserve criterion that is really the requested change, and the report shows every criterion's kind next to the task for a human. `kind` is required with no default: contracts are parsed only from the spec model's output (contract.json is never read back), and a silent default would hide an unlabelled criterion. Refactor-only tasks (no `change` criterion) are out of scope for v0.1 |

## Decisions for interactive mode
Source: the interactive TUI design (branch `feat/tui`), 2026-11-25.

| # | Area | Decision |
|---|---|---|
| 29 | Interactive session | `rewire` on a TTY opens a chat, then hands code changes to a gated run. The chat agent cannot write: its tools are `read`, `grep`, `find` and `bash` under the sandbox `chat` profile (no repo writes, scratch dir only, network denied). It has no `write` or `edit` tool. The chat model is the author model (`routing.spec`). One gated run is active at a time. Sessions are stored redacted in `.rewire/sessions/<id>.jsonl` and can be resumed. **Why:** every code change must pass the same hard gates and independent review as `rewire run`, so the conversational surface gets no write path of its own. **Accepted trade-offs:** chat `bash` ignores abort and runs to its own timeout (up to 600 s); it cannot write the repo, so the cost is a stray sandboxed process. Ctrl-C at a proposal card or the in-app trust prompt exits 0 (the chat is persisted and resumable) instead of dismissing the card. A `.rewire/sessions` file committed to a cloned repo is treated as the user's own history: `/resume` lists it (reading at most 64 KiB for its title) and replays it to the chat model like any stored session; the chat stays read-only and a proposal still needs `y`. |
| 30 | Claude skills | User skills load automatically from `~/.claude/skills` and `$XDG_CONFIG_HOME/rewire/skills`. Repo skills (`<repo>/.claude/skills`) load only after trust is pinned to a sha256 over all their files. The hash includes shadowed repo skills (a user skill with the same name wins), so the trust prompt lists them. A changed hash asks again. The trust store is `$XDG_CONFIG_HOME/rewire/trusted-skills.json`, updated with a locked read-merge-write. Skills are read on the host and snapshotted once per session; a trust granted mid-session takes effect on `/clear`. Skills reach the chat, spec, test-writer and implementer only, never the reviewers or the verifier. **Why:** a skill is instruction text from outside the contract. Repo skills are attacker-controllable, so they need an explicit, content-pinned approval, and the stages that judge the result must not be steered by them. The sandbox denies `~/.claude*`, so skills are read on the host and materialised under `$XDG_CACHE_HOME/rewire/skill-sets` (deliberately not the OS tmp dir, which the Linux sandbox replaces with a private tmpfs). On Linux, an `$XDG_CACHE_HOME` under `/tmp` therefore leaves a skill's bundled files unreadable inside the sandbox (SKILL.md itself still loads); the default `~/.cache` is unaffected. **Ruling:** the planned `skill_untrusted` error code was not implemented; pending repo skills are simply not loaded and `/skills` lists them as pending. A skill dir rejected at discovery (e.g. a symlink) is shown as a warning line at TUI start, and an unreadable trust store leaves repo skills unloaded with a warning instead of blocking the session. **Accepted residual:** skill text can still reach the reviewers indirectly, through the contract or the diff that an author stage produced. |
| 31 | Checkpoints | A run can pause for approval at `contract`, `tests` and `commit`. In the TUI, `contract` and `tests` are on by default and `commit` is off (`/checkpoints` changes it per session). Without a `checkpoint` input (`rewire run`, headless) nothing pauses. The contract checkpoint accepts `approve`, `revise(note)` or `stop`; the tests and commit checkpoints accept `approve` or `stop`. Revise is limited to 3 per run, and a 4th is recorded as `stop`. `stop` escalates with reason `stopped_by_user` (exit 2). An invalid decision escalates with `stage_error` and fixed preset text. Ctrl-C at a pending checkpoint ends the run as `interrupted`. Every decision is in `events.jsonl` and `report.md`. **Why:** approval must be possible without making the gates optional. A bounded revise loop keeps a run from becoming an open-ended chat, and a protocol fault must stop the run without asking a model to explain it. |
| 32 | Terminal text and approval | **One terminal sanitizer.** `sanitizeTerminal` in `@rewire/core` is the only one. It is a single linear scan that drops CSI and ESC sequences, OSC/DCS/SOS/PM/APC strings (7-bit and 8-bit), C0/C1 controls except newline and tab, CR, the Unicode default-ignorable code points (tags, variation selectors, zero-width and bidi marks, fillers) and U+2028/2029. The TUI's `sanitize` is that function. `stripControls` is the same function with tabs dropped as well. This changes #23 output in the report, the commit title and the headless stream: a terminated control string is removed whole, including its body and a CSI's final byte (the old regexes left parts of it). A string with no terminator before a newline or the end loses only its introducer, so mojibake such as `â€\u009d` cannot swallow the rest of a report. **Approve exactly what is shown.** `propose_run` refuses a task that the sanitizer would change, telling the model to resend plain text, and stores the accepted task redacted. The proposal card (`<Safe>` = `redact(sanitize(x))`) therefore shows exactly the string the run starts with. **Transcript.** Finished transcript entries are printed once through Ink's `<Static>`, cut to the terminal width at the time they are printed. They do not re-flow on resize. `/clear` and `/resume` start a new static region under a separator line. **Why:** hidden text in an approved task would reach the spec model as trusted input, which is the same "approve what was shown" property that the skill trust pin guarantees. Two sanitizers would drift. A transcript in the dynamic frame was rewritten, and duplicated into scrollback, on every keystroke once it was taller than the screen. |
| 33 | TUI parity with Claude Code / Codex | The interactive session streams replies, renders Markdown with syntax-highlighted code, shows tool calls as `● Name(args)` with a `⎿` preview, a spinner, a header box and a status line, a `/` command menu, an `@` file picker and checkpoint cards with scrollable views. **Streaming only from the chat.** Streaming is opt-in through `onDelta` on a provider call; only the chat agent passes it. Without it every provider sends the same non-streamed request as before. A pipeline test pins this: it wraps the providers of a faux pipeline run (reviewers and verifier included) and asserts that no call carries `onDelta`, while a faux-provider snapshot pins the stages' prompts and tool lists. So the pipeline, `rewire run`, `--headless`, the exit codes and the reports are unchanged. A stream that fails mid-way maps to the same codes as a non-streamed call (`ollama_timeout`, `ollama_request_dropped`, provider errors, `aborted`), and `REWIRE_OLLAMA_TIMEOUT_S` stays the whole-call wall clock. A throw from the `onDelta` callback itself fails the call with the new code `provider_stream_callback_failed`, never as a transport error. **Sanitize, then redact, the whole buffer.** Streamed text is rendered as `redact(sanitizeTerminal(buffer))` over the whole accumulated text on every render (throttled to 50 ms), never per delta, and only then split or capped, so an escape sequence or a key split across deltas, or a key split by an SGR sequence, is still caught. The same order applies to tool previews, the commit diff view and the contract and test views. **Scrollback.** Finished parts of a reply leave the live area as they finish: a tool line once its result arrives, text once its model call ends, and each complete top-level Markdown block as soon as the next one starts. A block is split off only at a blank line where cleaning the parts gives exactly what cleaning the whole buffer gives, so a split cannot cut a key or an escape sequence. They print once through `<Static>`, and only the block still streaming stays live, cut to the terminal height (its tail shows). A live area taller than the terminal would be re-printed into scrollback on every frame (DD #32). Chat events that arrive after their turn ended are dropped. Markdown is lexed from already clean text, and every leaf string is cleaned again after lexing, because `marked` decodes numeric references (`&#x1b;`) back into control characters. Markdown and highlighting become Ink `<Text>` segments with colour props, never raw ANSI. **Caps.** Lists and quotes nest at most 8 deep (deeper renders as plain text: unbounded nesting crashes yoga-wasm); a code block with a line over 2,000 characters, more than 5,000 lines or over 50 KB renders unhighlighted (highlight.js is quadratic on long tokens); highlighting is memoized per finished block; only the registered grammars are bundled. **Esc versus Ctrl-C.** Esc interrupts the chat reply in flight: the abort signal stops the provider request, the text already streamed stays on screen marked `Interrupted by user`, and the turn is not stored. Esc never aborts a gated run; Ctrl-C keeps its meaning (it aborts a run or a turn, quits when idle, and a second press within 1 second exits 130). Esc still cancels the revise box and closes the `/` menu, the `@` picker and a checkpoint view. **`ctx`** in the status line is the last chat model call's input plus output tokens, the size of the chat's context, as Claude Code and Codex show it, not a sum over the session. **The `@` picker only inserts a path.** It lists `git ls-files` on the host, spawn-streamed and killed once 5,000 usable paths are in (paths with control or terminal-unsafe characters are dropped). Choosing one inserts the path text; the chat agent reads the file with its own sandboxed tools, so the picker grants no access the chat did not already have. **Why:** the session should feel like the agents people already use, without letting the polish reach the gated pipeline or the terminal. Streaming in the pipeline would add a failure mode to every stage for a view nobody watches; per-delta cleaning misses anything split across chunks. Esc is the common interrupt key in both reference tools, but a run is expensive and has its own report, so it keeps the deliberate Ctrl-C. **Accepted residuals:** a key split by a literal newline is not redacted (inherent to the redact patterns; a fragment of a wrapped key can show in a preview); OpenAI and Anthropic streams have no wall-clock bound of their own (only the TUI streams, and Esc aborts a hung stream); `ctx` counts chat calls only, not a run's stages. |
| 34 | Chat context compaction | **A checked record, not a summary.** The chat's context is compacted into a structured session record (`goal`, `constraint`, `preserve`, `decision`, `open_question`, `preference`, `next_step`, `note`). Each item has a `source` (`user` or `inferred`), evidence (`{messageId, quote}`) and a status. A separate `observed` block (files read, commands and their exits, tool failures) is computed by code from stored messages, never by the model. Its schema also has a `runs` list, which the chat session never fills in v0.1 (the chat model does not see run outcomes; see the residuals). The model returns operations (`add`, `update`, `resolve`, `supersede`) and code applies them. **Authority rules, all checked by code.** (1) Every cited quote must appear verbatim in the cited stored message (after the store's sanitize and redact); quotes under 12 characters must be the whole message. (2) A `user` item can be created, changed or superseded only with evidence from user-role messages. Tool output, file contents, skill text, assistant text and the existing record never create or override one. (3) The evidence for changing a `user` item must be in the compaction window, or recent, or pending (see below). (4) It must also be newer than the item's newest evidence (`stale_evidence`), so an old instruction cannot overturn a newer one. (5) Superseding a `user` item needs `by.source` user. (6) One op per item per compaction (`duplicate_target`), and a snapshot check (`state_changed`) rejects an op whose target changed since the verifier saw it. (7) A `skill` or `recall` tool result is never evidence: an op citing one is rejected (cite the original message). (8) An `inferred` item that no user message supports (its evidence cites only tool results or assistant replies, or nothing) gets a code-set `notFromUser` flag and renders as `[inferred, not from the user …]`. The chat prompt and the record preface say that only `[user …]` items carry the user's authority and that `inferred` items are the compactor's reading, never instructions. So a file line such as "the user has decided X" can at most become an item visibly marked as not from the user, and a goal, constraint, preserve or decision that cites only it is applied only if the verifier accepts it (below). **No silent loss.** An item leaves the active record only through `resolve` or `supersede` with evidence, and goes to the archive (capped at the newest 500 in the stored line; the full history stays in the message log). A user message cited by an op that was rejected for a reason other than a failed authority check (a verifier reject, `duplicate_target`, `verification_budget`) stays citable for 3 compactions (`pending`), so a junk op cannot block a later correction. A compaction that fails (invalid output after one retry, a provider error, a violated invariant, an unavailable verifier) keeps the previous record and the raw messages since it, shows one dim line, and the session continues. When a window was split into parts, the parts already applied stay and the context ends there. After a failure the automatic trigger is held back until the context has grown by a quarter of the limit, capped at a ceiling of `limit + 0.5·(0.85·W − limit)`; an attempt already at or past that ceiling turns automatic compaction off for that window (`stuck`, shown once; `/compact` still works, and a changed window clears it). The `recall` tool searches all stored messages and the archive, so detail that left the context can be found. **Cross-family verifier.** Risky ops (`isRiskyOp`: any op on a `user` item; an add or supersede that creates a `user` item; any update, resolve or supersede of an open question; and an add, update or supersede that leaves an inferred goal, constraint, preserve or decision resting on tool results with no user message among its evidence) go in one batch to the run's verifier model (`routing.verifier`), from a different family than the chat model when the routing allows it. It sees the op, the target item as it is in the record, the cited messages and whether they are in the window, all fenced and cleaned (never skill text or `recall` output, which cannot be cited), and answers with exactly one JSON object (anything else is retried once, then rejects). An explicit reject drops that op. If the verifier is unavailable, times out (180 s) or never decides, the whole compaction fails, because skipping the check would let an unchecked change through. **Deterministic rendering.** The record the model sees is rendered by code from the record, under a budget, inside `fenceUntrusted` (`untrusted_session_record`). Nothing rendered is stored: a compaction line stores the record, the compaction point (`since`), the retained range and any cut of its newest message (`retainedFrom`, `truncated`), the fence id and the render budget. A `recordMessage` or cut `content` found in an older or forged line is ignored. On resume the context is rebuilt from those fields and the stored messages, so it is byte-identical and the prompt prefix stays stable for caching; a cut is measured and applied on the redacted text the store writes, so it lands on the same characters live and after a resume. **Context shape.** After a compaction the context is the system prompt, the record, one message of the most recent user messages verbatim (budget min(`recent_user_tokens`, 0.25·limit); the newest alone over it is cut head and tail), and the turns after that point. Assistant and tool turns from the compacted region are dropped. Compaction splits a window too big for the model's prompt into consecutive parts, each stored on its own. Only the last part's context is fitted: to a target of min(0.5·limit, limit − the pending message), first by halving the retained budget (down to none), then by halving the record's render budget (down to 0; `user` items are never dropped). If even that smallest form is over the target, the compaction still applies, reports `overBudget`, and holds the automatic trigger back the same way as a failure (or marks it `stuck`). So the result is not guaranteed to be under half the limit: many long `user` items on a small window can keep it above. **Trigger.** The limit is the smallest of: the formula `min(0.85·W, 32768·(W/32768)^0.6)` rounded down to 1000, or instead the calibrated value when one exists (which may be above the formula); 0.85·W rounded down to 1000; and a latency candidate (measured prompt-reading rate × `latency_budget_s`, after 2 samples). The first sample after a model load is skipped (it includes load time). That value is raised to at least 4096 and then capped at 0.85·W, so a window under about 4.8K gets a limit below 4096. A configured `[compaction.models."<ref>"] limit` replaces the computation and is floored at 4096 but not capped. `rewire calibrate` measures the effective context with planted-fact probes, never runs by itself, and requires `--yes` on a paid provider; its results are keyed by model digest and window and go stale when the window moves more than 10%. The plan asked for "a token and cost estimate" before a paid run; the code prints an input-token count only (rewire has no price table) and exits with `calibration_failed` without `--yes`. Compaction applies to the chat only. `rewire run`, `--headless` and every pipeline stage are unchanged, and skills, `recall` and the record never reach the pipeline's reviewers or its run verifier (#30). The compaction verifier is a separate checker: it sees the record item it judges, but never skill text or `recall` output. **Why:** a summary written by the model is unchecked prose, and the first thing it forgets is a constraint, or it keeps a line a file injected. A record whose edits code verifies, whose user-authority is tied to user messages, and whose removals leave a trace gives long chats a memory that cannot be rewritten by tool output and that fails closed. A second family checks the edits that matter because a model reviewing its own edit shares its blind spots. The formula comes from the observation that long contexts are read less reliably and re-read every turn, so the limit grows slower than the window; calibration replaces that guess with a measurement when it matters. **Accepted residuals:** judgement in `inferred` items can be wrong (code checks the quote exists, not that the inference is sound); the formula constants (0.85, 32768, 0.6) are judgement; a key split by a literal newline is not redacted (as in #33); with a single model the verifier is not independent, and the TUI shows a notice; a provisional window (Ollama before its first reply, faux) is not checked for staleness against a calibration until the first turn refreshes it; a hung, abandoned compaction blocks the next `/compact` (compactions queue); calibration is slow on local models, and two calibrate runs at once are not locked against each other (each write is atomic, the last writer wins); an inferred item resting on an assistant reply that repeats injected text is marked not-from-the-user but is not sent to the verifier (only evidence that cites a tool result and no user message is), because routing every assistant-backed decision through it would cost a verifier call on most compactions; `observed.runs` is never filled by the chat (feeding run outcomes would need the session to learn and persist them, a new channel into the record, for a fact the TUI already shows); the same session resumed in two processes at once interleaves message ids, so compaction lines from one are refused by the store and its automatic compaction ends `stuck` (a conflict check on append would need a new error code and a reopen path, and concurrent writers were already unsupported before compaction); on a very small window (W under about 6K) the compactor's prompt budget is about 1,000 tokens, close to its own system prompt, so a compaction becomes one model call (and possibly a verifier call) per turn of the window: slow on a 4K Ollama model, but never unsafe. |
| 35 | Cloud and API providers | **Platform clients, not a changed URL.** Claude on Bedrock, Vertex and Foundry uses each platform's own SDK client (`AnthropicBedrockMantle`, `AnthropicVertex`, `AnthropicFoundry`), so signing (SigV4, Google ADC, Foundry key header) and URL shapes are the SDK's, and the request body is still `toAnthropicParams`. Azure OpenAI uses `AzureOpenAI`; Gemini and `[endpoints.<name>]` use the OpenAI client against an explicit `baseURL`. Every client is given explicit credentials and base URL, so the SDKs never read ambient env (`OPENAI_BASE_URL`, `OPENAI_API_KEY`, org and project ids), and `OPENAI_CUSTOM_HEADERS` is neutralised for everything but the plain `openai` provider, and `ANTHROPIC_CUSTOM_HEADERS` (read by the Anthropic SDK from process.env) for everything but the plain `anthropic` provider: every name either holds is passed as a null default header, so it is removed before Bedrock signs and before Vertex adds its token, and the platform's own credential is set after it (a user header must never replace another vendor's credential or be sent to it). **Families never come from endpoint names.** The user picks that name, and independence is security-relevant: an endpoint's family is its `family` key, else the model id (vendor path segment such as `anthropic/`, then the model name, then the Ollama rules). Router or meta ids (`auto`, `router`, `default`, `openrouter/...`) fail closed with `model_ref_invalid` unless `family` is set; bedrock, vertex and foundry accept Claude only. A `gemini:` Gemma id is `gemma`, as on endpoints and Ollama (the Gemini API serves Gemma, and the same weights must never review themselves). Azure serves other vendors' models under deployment names the user picks, so `azure:` takes `[providers.azure] family` when set, else a vendor word at the start of a word in the deployment name (`DeepSeek-R1` is `deepseek`), else `gpt`; a name that hides its model is an accepted residual (set `family`). **Secrets.** `models.toml` names env vars (`api_key_env`), never holds keys; base URLs must be https (http only on loopback) with no userinfo, query or fragment, and the SDK base-URL env overrides follow the same rule; a keyless loopback endpoint sends no auth header; SDK errors are redacted of keys, tokens and signed-URL parts. Doctor prints resolved values and env var names only, hides values of an unusual shape as `(set, unusual format)`, and treats an unused broken table as a note. The calibrate paid gate covers every provider except ollama, faux and loopback endpoints. Cloud SDKs are imported lazily (they are not loaded unless used) but are bundled in the npm package. `rewire run` and `rewire chat` create every routed role's provider once before starting (creation only resolves settings and env, with no request), so a misconfigured reviewer or verifier fails with `provider_auth_missing` before anything is billed, not at its stage; the pipeline still creates its own. Azure `api_version` is required (the SDK has no default) and the endpoint must be the resource root. No new error codes. **Accepted residuals:** an unrecognised leading word in a model id counts as its own family, so an exotic id can pass as independent (set `family`); the Vertex fix for unhandled credential rejections reads the SDK's private `_authClientPromise` (a test guards it); loading ADC cannot be aborted; Azure `max_completion_tokens` may be rejected by very old API versions; Gemini's output-cap field `max_tokens` is documented on Vertex's compatibility page but not confirmed against Gemini's own reference; bundle growth (sheperd tarball 1,137,726 to 1,608,352 bytes, +41%; `dist/main.js` about +2.4 MB unminified); a secret shaped like a resource name could still be printed by doctor (a malformed region or resource is never echoed in an error); doctor exits 1 for a used but incomplete provider; the calibration cache is keyed by `<endpoint>:<model>` and the window digest, not the endpoint's `base_url`, so re-pointing an endpoint at another server keeps the old result until `rewire calibrate --fresh` (mixing the URL in would invalidate every existing cache entry); the cloud and OpenAI-compatible clients still honour `ANTHROPIC_LOG`/`OPENAI_LOG` from process.env, as the first-party providers do (debug output only, never a request change). **Not supported:** Claude subscription login, because Anthropic does not permit third-party apps to offer Claude.ai login or route requests through Free, Pro, Max or Ultra credentials. |
