# Releasing sheperd to npm

rewire is published as one npm package, **`sheperd`**, plus four platform packages that each
hold a prebuilt `rewire-sandbox`: `sheperd-darwin-arm64`, `sheperd-darwin-x64`,
`sheperd-linux-x64` and `sheperd-linux-arm64`. The `@rewire/*` workspace packages are private
and are never published (they are bundled into `sheperd`).

| what | where |
| ---- | ----- |
| the `sheperd` manifest (version, optionalDependencies, files) | `npm/sheperd/package.json` |
| bundle, stage, check and pack | `scripts/npm/build.mjs` |
| install the tarballs and smoke-test them | `scripts/npm/smoke.mjs` |
| CI and publishing | `.github/workflows/release.yml` |

The platform packages' manifests are generated from `npm/sheperd/package.json`, so the version
lives in one file: `version` and the four `optionalDependencies` pins, which must all be equal
(`build.mjs` refuses anything else).

## How the sandbox binary is trusted

The sandbox is the security boundary (design decision #21), so the published CLI only runs a
platform binary it can verify:

- **Hashes recorded at build time.** `build.mjs sheperd` runs after the four binaries are
  staged and records each one's sha256 in the bundle (`REWIRE_BUNDLE_SANDBOX_SHA256`). In the
  release workflow the `package` job downloads the four native builds first, then bundles with
  `--all-platforms`; `build.mjs pack` refuses a bundle that does not record the hash of every
  binary packed with it.
- **Verified before use.** The installed CLI finds `sheperd-<os>-<arch>` only next to itself
  (`<sheperd>/node_modules/<name>`, or the hoisted sibling `<node_modules>/<name>`; never via
  `NODE_PATH`, `~/.node_modules` or other ancestor folders) and checks its `package.json`
  version against the CLI's and the binary's sha256 against the recorded one. Any mismatch, a
  missing or non-executable binary, or a package directory without a `package.json` fails closed
  (`binary_missing`) and never falls through to `PATH`. A substituted or hijacked platform
  package therefore cannot get its binary run, even with the right name and version.
- **Not checked:** `REWIRE_SANDBOX_BIN`, the checkout's `target/` (source builds only; the npm
  bundle never looks there) and `PATH` are the user's own choice and are used as found.
- **On the registry.** The publish job compares each package's registry `dist.integrity` with
  the local tarball's sha512 before publishing anything and again afterwards (see below).

Each platform package also ships `THIRD_PARTY_LICENSES.md`, the licences of the Rust crates
linked into that binary, generated by `build.mjs platform` from `cargo metadata --locked` for
the target. The Linux packages declare `"libc": ["glibc"]`, so npm skips them on musl systems
(Alpine) and `rewire doctor` reports a missing binary instead of an exec failure. Release
binaries are built with the Rust toolchain pinned in `release.yml` (`RUST_TOOLCHAIN`).

## One-time setup

The workflow cannot do these for you; it refuses to publish until they are in place.

1. **npm account.** Create an account at <https://www.npmjs.com/signup> and turn on two-factor
   authentication (Account settings, "Two-Factor Authentication", mode "Authorization and
   writes").
2. **Claim the five names now.** `npm view <name>` returning `E404` only means nobody holds the
   name today; an unpublished name (as `sheperd` once was) can be taken by anyone, and the names
   and the first version are public in this repository. Publish a placeholder for each of
   `sheperd`, `sheperd-darwin-arm64`, `sheperd-darwin-x64`, `sheperd-linux-x64` and
   `sheperd-linux-arm64` by hand, e.g. version `0.0.0-reserved` with a one-line README, under
   `--tag reserved`. If any name is already taken, the names must change everywhere
   (`npm/sheperd/package.json`, `platformPackageName` in `packages/sandbox/src/client.ts`,
   `build.mjs`, the workflow).
3. **Trusted publisher on npm.** The workflow authenticates by npm trusted publishing (OIDC);
   no npm token is created or stored. On npmjs.com, for each of the five packages: Settings,
   "Trusted Publisher", GitHub Actions, organization or user `Abubakarjutt`, repository
   `sheperd`, workflow filename `release.yml`, environment `npm-publish`. Then, under
   "Publishing access", choose "Require two-factor authentication and disallow tokens":
   trusted publishing still works, and a leaked token cannot publish. Do not create a token
   with "bypass 2FA".
4. **GitHub environment `npm-publish`.** The `publish` job runs in this environment and checks
   it before publishing. In the repository: Settings, Environments, "New environment", name
   `npm-publish`:
   - **Required reviewers:** add yourself (and anyone else allowed to release). Every publish
     then waits for an approval.
   - **Deployment branches and tags:** "Selected branches and tags", add a **tag** rule `v*`
     (and no branch rules).
   - **No secrets.** There is no `NPM_TOKEN`; npm trusts this workflow in this environment.

   If the environment is missing (GitHub would create an unprotected one on the fly), has no
   required reviewer, or is not limited to the `v*` tag pattern, the publish job fails with an
   error naming what is missing. If the trusted publisher on npm does not match (repository,
   `release.yml`, `npm-publish`), `npm publish` fails with an authentication error.
5. **Tag ruleset.** Settings, Rules, Rulesets, "New tag ruleset": target tags matching `v*`,
   enforcement Active, rules "Restrict creations", "Restrict updates" and "Restrict deletions",
   with only yourself (or a release team) in the bypass list. Without it anyone with push access
   can create a `v*` tag on any commit.

## Before tagging

- The version in `npm/sheperd/package.json` (and its four pins) is the version to release.
  The first published release was `0.1.0-beta.2`. (The tag `v0.1.0-beta.1` exists, but its run failed
  before publishing anything, so `0.1.0-beta.1` was never released.)
- `main` is green in CI. The `ci` workflow's "npm package smoke test" step packs, installs and
  smoke-tests the packages on Linux x64 and macOS arm64 on every push and PR.
- Optionally run the release pipeline without publishing: Actions, `release`, "Run workflow"
  with `dry-run` ticked (the default). It builds all four binaries on native runners, packs all
  five packages, smoke-tests them, and stops. It also runs, always as a dry run, on pull
  requests that change the packaging.
- Locally (macOS arm64 example):

  ```sh
  pnpm install --frozen-lockfile && pnpm -r build
  node scripts/npm/build.mjs sandbox     # release build, local paths remapped
  node scripts/npm/build.mjs platform    # this host's sheperd-<os>-<arch> + crate licences
  node scripts/npm/build.mjs sheperd     # after platform: records the binary's sha256
  node scripts/npm/build.mjs pack        # checks npm pack --dry-run, writes dist-npm/tarballs/
  node scripts/npm/smoke.mjs --faux-run  # installs (project and -g, offline): --help, doctor,
                                         # a tampered binary refused, a verified faux run
  ```

## Publishing a release

```sh
git checkout main && git pull
git tag v0.1.0-beta.3
git push origin v0.1.0-beta.3
```

The tag push runs `release.yml`:

1. `plan` fails the run if the tag is not `v` + the version in `npm/sheperd/package.json`.
2. `sandbox` builds `rewire-sandbox --release` with the pinned toolchain on `macos-15` (arm64),
   `macos-15-intel` (x64), `ubuntu-22.04` (x64) and `ubuntu-22.04-arm` (arm64). Each runner
   checks the binary's header matches its target, that no path of that runner (its home or
   checkout) is embedded in any packed file (`build.mjs check`), and on Linux that it needs no
   glibc newer than 2.35; then uploads it.
3. `package` downloads the four binaries, bundles `sheperd` with their sha256s, checks and packs
   all five packages, and smoke-tests the tarballs.
4. `publish` waits for the `npm-publish` environment's reviewer, checks the environment, then:
   - compares every package's registry `dist.integrity` (if the version exists) with the sha512
     of the local tarball, and **fails before publishing anything** on a mismatch (a squatted or
     hijacked `name@version`);
   - runs `npm publish --provenance --access public --tag next` for the four platform packages,
     then `sheperd`, skipping only a version already on the registry with exactly these bytes
     (a re-run after a partial publish);
   - re-reads the registry and fails unless all five serve exactly the local tarballs.

A manual dispatch from the tag with `dry-run` unticked publishes the same way. A dispatch from
a branch with `dry-run` unticked fails: publishing always comes from a tag.

Check the result:

```sh
npm view sheperd dist-tags
npm i -g sheperd@next && rewire doctor
```

## Dist-tags: `next` and `latest`

Releases are published with `--tag next`. **The very first publish of a package is the
exception:** a package with no `latest` gets one, so after the first release `latest` also
points at `0.1.0-beta.2` and a plain `npm i -g sheperd` installs the beta. That stays true until
`latest` is moved (a stable release, or by hand). If you claimed the names with a placeholder
(one-time setup, step 2), `latest` points at that placeholder instead; move it after the
release:

```sh
npm view sheperd dist-tags                    # see where latest and next point
npm dist-tag add sheperd@0.1.0-beta.3 latest  # promote a release (or move latest back)
```

Later pre-releases only move `next`. To promote one, run `npm dist-tag add sheperd@<version>
latest`. The platform packages need no promotion: `sheperd` pins their exact version.

## Yanking a bad release

`npm deprecate sheperd@<version> "<reason>"`, then move the dist-tags back:
`npm dist-tag add sheperd@<good version> next` (and `latest` if it points at the bad one).
`npm unpublish` is only possible within 72 hours and blocks the version number forever; prefer
deprecating and releasing a new version.
